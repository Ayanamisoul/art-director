# Лендинги из примера — дизайн (v2)

Дата: 2026-11-23. Статус: ожидает согласования.
v2 по замечанию заказчика: правила оформления из примера должна считывать
модель, а не только детерминированный парсер токенов.

## Замысел и мотивация

HTML-пример — это уже готовая инструкция по построению лендинга: в нём есть
фон, подвал, блоки, цвета, шрифты, отступы, рамки для фото. Сейчас оформление
лендингов статично: три стиля зашиты в коде (`landing_styles/*.css`), новый
добавляет только разработчик. Презентации при этом берут оформление из
загруженного образца PPTX/PDF.

Цель: менеджер загружает HTML-страницу как **пример оформления**. Модель
читает её правила — «знает, куда смотреть» — и переносит их в новый лендинг
с другой информацией. Код гарантирует, что результат безопасен, автономен
и предсказуем в структуре.

## Цели

- Загрузка примера через интерфейс «Чаты и лендинги» и через API.
- Модель один раз читает пример и пишет CSS-профиль под структуру
  классов проекта: фон, шапка/подвал, блоки, типографика, отступы,
  оформление кнопок и рамок фотографий.
- Дальнейшая сборка лендингов с этим примером — детерминированный код:
  тот же контент-контракт (`title`, `lead`, `sections`, `brand`, `cta`,
  `image`, `font_id`), та же структура классов, что у встроенных профилей.
- Правка существующего лендинга сохраняет стиль (round-trip брифа).
- Встроенные профили `glavbuh`, `school`, `law` работают как раньше.
- `save_landing` через MCP принимает имя примера как `profile`.

## Не-цели и анти-цели

- Не вставляем HTML/JS/CSS примера в готовый лендинг: модель пишет
  CSS только под наши классы; страница остаётся автономной и безопасной.
- Модель не меняет структуру страницы (разметку) — только оформление.
- Не поддерживаем внешние стили примера (`<link href=…css>`): только то,
  что внутри файла (`<style>`, `style=`). «Сохранить как HTML-только»
  подходит, «страница с папкой» — нет.
- Не добавляем `<video>` в контракт лендинга: правила оформления видео
  из примера переносятся на общие медийные рамки (`.hero-media img`).

## Подходы

1. **Модель читает правила примера → валидированный CSS-профиль (выбран).**
   При загрузке примера один вызов модели: ей отдают очищенные стили и
   структурный скелет примера + шпаргалку наших классов; она возвращает
   CSS под нашу структуру. Код проверяет CSS (белый список селекторов,
   запрет внешних ресурсов, лимиты), кэширует как профиль примера.
   Плюсы: переносит именно «правила» — палитру, типографику, отступы,
   рамки, фон и подвал, а не огрызки токенов; стиль генерируется один
   раз, все последующие сборки — чистый код без модели. Минусы: нужен
   настроенный ключ модели на загрузке; качество CSS зависит от модели —
   компенсируется валидацией и фолбеком.
2. **Только детерминированные токены + параметрический CSS.** Быстро и
   без модели, но переносит лишь цвета/шрифт/ширину/радиус — не «правила»
   целиком. Отвергнуто как основной путь (замечание заказчика);
   используется как **фолбек**, когда модель недоступна.
3. **Свободный HTML через `save_html`.** Уже есть, но теряет контракт
   структуры (разделы, навигация, подразделы, round-trip для правок).
   Отвергнуто для этого сценария.

## Устройство

### Хранилище примеров — `agent/core/landing_examples.py` (новый)

- Каталог `data/landing_examples/` (в git не попадает).
- `list_names()` — имена `*.html`; `newest()`; `accept_upload_bytes(name, data)`:
  файл обязан выглядеть как HTML (есть `<html`/`<body` или `<style`),
  лимит 8 МБ; при сохранении вырезаются `<script>` и атрибуты `on*`,
  data:-URL обрезаются до заглушек (для хранения и для модели).
- Рядом со примером живёт сгенерированный профиль: `<имя>.css`.
  Перезагрузка примера → перегенерация CSS.

### Чтение правил моделью — `design_from_example()`

Один вызов `llm.chat()` (без инструментов, тот же бэкенд, что у чата):

- **Куда смотреть — готовит код:** из примера извлекаются все `<style>`
  (включая `@media`), `style=` у ключевых тегов и скелет структуры —
  список тегов/классов `body → header/footer, hero, секции, заголовки,
  списки, картинки` с их стилевыми правилами. Data:-URL и скрипты
  вырезаны; всё упаковано в ~20К токенов.
- **Задание модели:** «вот правила оформления примера, вот скелет наших
  классов (`:root`-переменные, `.hero`, `.chapter`, `.items`, `.button`,
  `.hero-media img`, шапка, подвал, мобильная адаптация) — напиши CSS,
  который переносит оформление примера: фон страницы, шапку и подвал,
  hero, типографику, отступы, кнопки, рамки фотографий. Без url(),
  @import, @font-face с внешними src».
- **Валидация кодом** (`validate_profile_css`): баланс скобок; селекторы
  только из белого списка наших классов/тегов/медиазапросов; запрет
  `url()` (кроме `data:`), `@import`, внешних `@font-face`; лимит ~48 КБ;
  обязательны `:root` c `--ink`/`--ground` (иначе дописываем дефолты).
  При провале — один повтор с текстом ошибок; затем фолбек.
- **Фолбек:** детерминированные токены (палитра, шрифт, ширина, кнопка —
  минимальный парсер CSS, как в v1) + параметрический CSS. Загрузка
  без ключа модели всё равно работает, ответ помечает «стиль упрощён».
- Успешный CSS кэшируется: `data/landing_examples/<имя>.css`, с комментарием
  о происхождении (модель, дата). Плюс копия рядом с артефактом при первом
  сохранении лендинга (`data/artifacts/<лендинг>.profile.css`) — если
  пример потом удалят, старые лендинги пересобираются по копии.

### Сборка — изменения в `core/landings.py`

- `render_landing`: `profile` ∈ PROFILES → встроенный стиль; иначе ищем
  пример: `examples/<имя>.css` → `artifacts/<лендинг>.profile.css` →
  фолбек-токены; иначе ошибка со списком доступного. `data-profile`
  получает значение `profile` как есть — round-trip брифа сохраняется.
- Пользовательский TTF (`font_id`) по-прежнему переопределяет шрифт —
  правило примера уступает явному выбору пользователя.

### Веб-интерфейс и API

- `GET /api/landing/profiles` → `{"profiles": {...}, "examples": [имена]}`.
- `POST /api/landing/examples` — загрузка (multipart), как `POST /api/templates`;
  ответ сообщает, прочитан ли стиль моделью или собран фолбеком.
  Новый роутер `routers/landing_examples.py`.
- Селектор «Образец лендинга» наполняется встроенными профилями и
  примерами. Кнопка загрузки шаблонов принимает и `.html`.
- `web.py`: проверка `profile` пропускает имена примеров; системный
  промпт называет выбранный пример; пин `save_landing.profile` не меняется.
- «Авто»: если примеры есть — самый свежий, иначе прежний дефолт `glavbuh`
  (симметрично «Авто» шаблонов презентаций). Мой выз; легко поменять.
- Автодетект брендов в брифе — без изменений, встроенные приоритетнее.

### Промпты, MCP, документация

- `prompts.py` (LANDING_DESIGNER): стиль — встроенный профиль **или** имя
  загруженного примера.
- `mcp_servers/artifacts.py`: docstring `save_landing` упоминает примеры;
  ошибка при неизвестном `profile` перечисляет встроенные профили и
  загруженные примеры (внешний агент узнаёт имена без нового инструмента).
- `README.md`: раздел «Лендинги» и таблица «Где лежат файлы».

## Ограничения и риски

- Качество переноса правил зависит от модели; белые списки защищают
  структуру и автономность, но не «вкус». Судья-лендингов работает как
  раньше; визуальную точность проверяет человек в предпросмотре.
- Пример, сохранённый «с папкой» (внешние CSS), даст фолбек-токены.
- Внешние шрифты примера (Google Fonts и т.п.) не загружаются — только
  `@font-face` с `data:` либо системный стек; шрифт можно приложить
  своим TTF, как сейчас.

## Проверка

1. `py -m unittest discover -s tests -v` — новые тесты (модель мокается):
   - валидация CSS: пропускает корректный профиль; режет `url()`,
     `@import`, посторонние селекторы, разбаланс скобок, лимит размера;
   - очистка примера: `<script>`/`on*`/data:-URL вырезаются;
   - фолбек-токены из файла без стилей; отклонение не-HTML, лимит 8 МБ;
   - рендер с примером: автономность, детерминизм, `data-profile`,
     round-trip `save_landing`/`read_landing`, копия `.profile.css`;
   - встроенные профили не изменились (существующие тесты).
2. `py test_mcp.py` — MCP-путь: `save_landing` с `profile` = имя примера.
3. Ручной сценарий с реальной моделью: загрузить `lab22_school.html`
   как пример → проверить сгенерированный CSS (палитра/шрифт School),
   собрать лендинг на другую тему, узкий экран, PDF-экспорт
   (`POST /api/landing/{имя}/pdf`).

## Что осталось строителю

- Точная шпаргалка классов в промпте дизайнерского вызова и пороги
  фолбек-токенов — на усмотрение реализатора, фиксируются тестами.
- Подписи опций селектора (с расширением или без) — решает реализатор.
